## Exact local demo

Start `npm run dev` if needed, then open **http://127.0.0.1:5173/?design=plans**. This development-only simulator uses synthetic ballot fixtures and the real organizer/guest React components with an in-memory transport. It makes **no account/API/database/provider requests** and creates **no working real shared link**. Reload resets its simulated state. Real HTTP/persistence checks are separate disposable PostgreSQL tests.

1. In **Organizer demo**, choose **Show demo results → Add to shortlist** on the sample walk. Optionally add a sample event or manual idea, up to three total. **Save shortlist → Preview ballot → approve → Publish ballot**.
2. Choose **Guest ballot demo**, select the walk and **Submit vote**. Return to **Organizer demo → Refresh plan & attendance**. The choice list shows ballot version, tally/ties and response counts. Choose an option explicitly, then **Use chosen option**. No winner or RSVP is inferred from the vote.
3. In **Public plan draft**, enter **November 21, 2026**, **15:00**, **America/New_York**, and **Synthetic park north gate** as the meeting point. Add public instructions if desired. Leave cost/booking uncertainty visible. **Save plan draft → Preview shared plan**. Review the exact fields/change notice and check approval, then **Confirm & publish plan**.
4. Choose **Create / replace plan link → Guest plan demo**. The demo link is expressly simulated. Enter **Sam**, choose **Going**, affirm that you reviewed the current version, then **Send RSVP**. Return to **Organizer demo → Refresh plan & attendance**: one Going response. The vote remains one vote separately.
5. Change **Plan local time** to **16:00 → Save plan draft → Preview shared plan → approve → Publish plan update**. The published version changes; the old RSVP moves to **needs reconfirmation**, out of current Going/Maybe/Can’t counts. The shared link does not change.
6. Choose **Guest plan demo → Reload shared plan / my RSVP**. Read the prominent change notice and 16:00 time, affirm the current version and **Reconfirm RSVP**. Back in organizer view, refresh: one current Going again. You can choose Maybe or Can’t make it and submit an update independently of the vote.
7. Try **Close RSVPs** or **Cancel plan**, with an explicit public reason/confirmation. Reload the guest plan to see the current notice/status and disabled responses. Cancellation/completion is terminal; no messages are sent. To test another lifecycle, reload the simulator and start a new plan. **Revoke plan link** ends guest read/edit access.

The offline UI test follows ballot → vote → proposal → approved plan → Going → changed time → reconfirm → cancellation while rejecting any real fetch. This is UI simulation evidence, not a browser, database or hosted-account claim.

## Normal organizer flow and exact approval

Reopen an owned saved planning session. Its discovery/save area now includes **Choose & publish a plan** beneath the shortlist/ballot controls. Refresh after publishing a ballot to load its current tally. The organizer chooses a specific option from a specific published ballot version; a tie is shown honestly, never resolved automatically. Selection records the ballot ID and immutable approved option snapshot, creates a **proposed** plan, and initializes a separate editable public draft. Unknown/ambiguous date strings are not parsed into invented exact dates.

Plan draft edits do not change the shared page. **Save plan draft** is separate from Save session and Save shortlist. Date, local clock time, IANA time zone and a nonempty meeting point are required to publish. Impossible dates, missing values and ambiguous/nonexistent DST clocks are rejected. Cost amount null remains unknown; zero remains zero. Starting price, per-person/group basis and currency retain their meaning. A new proposal always carries an exact-date venue/event schedule check: source hours or an event listing from another date do not establish the selected plan’s availability. Time and source links use the organizer’s explicit public details; Fuzl does not independently validate a booking or schedule against a live source.

Preview contains the exact activity, date/local time/zone, meeting point, cost/certainty, public links, instructions, unresolved checks, sample label and booking wording. **Confirmed** means the organizer’s group agreement, not verified feasibility, paid tickets, attendance or an API booking. The default says **Group agreed; booking / tickets still need arranging**. If the organizer records booking arranged, the page labels it **Organizer reports booking arranged**, with a reminder to check ticket/seat conditions. Unknown availability, fees, hours, duration, travel time and other requirements remain visible unless explicitly corrected in the public draft. A vote cannot waive a firm constraint, and a plan agreement does not certify an excluded option as feasible.

Publishing requires a saved matching preview, explicit approval and a public change notice. A server-computed draft fingerprint is included in the approval contract: refreshing metadata cannot make an older preview approve newer unseen draft fields. Session/plan revisions, edit counters and an explicit saved-draft reload protect concurrent/local changes. If an action’s response contains a draft changed again by another writer, local edits remain unsaved until reload/review. All published versions retain their own snapshots; source-listing or ballot changes never rewrite the plan silently.

## Stable links, lifecycle and change notices

**Create / replace plan link** provides a copyable `/plan#invite=…` URL for pasting into an existing group chat. Fuzl sends nothing. Content updates use the same active link; guests opening/reloading it get the current published version. Existing open pages are not live subscriptions: guests must reload to see a later change, and the server rejects responses to an obsolete plan version. Every published update carries a prominent notice. Material changes add a server-generated reconfirmation notice; cancellation is prominently labeled **CANCELLED** regardless of the organizer’s reason.

The UI creates a 14-day link; the validated API also allows 1 or 7 days. Server checks expiry and revocation on every read/write. Only token digests are stored. The organizer sees the plaintext link only in the current workspace, with a retained private mutation attempt for immediate retries; reload cannot recover a plaintext token. Replacing the link explicitly revokes the old one. Existing respondents who open the new link in the same browser can restore their own same-plan RSVP; the shared link itself grants no right to edit someone else’s response. Revocation blocks access; it does not delete plan history or attendance records.

Lifecycle transitions: proposed → confirmed or cancelled; confirmed → a new confirmed version, completed or cancelled. Completed/cancelled plans cannot be reopened or edited; use a new saved session for another outing. Cancelling a proposal that was never published creates no public page. **Close RSVPs** closes new/changed responses while retaining read access through a valid link. It stays closed across later publications; there is no automatic reopening. Terminal and closure changes use the last published snapshot, so an unfinished draft cannot leak into a cancellation/completion page.

## RSVP identity, privacy and reconfirmation

The guest plan route is outside organizer sign-in. Invite fragments are stripped before React/network work and kept in a separate tab sessionStorage slot. Tokens go only in headers (and explicit private creation payloads), never API URLs/logs. Guests read only the current approved plan and their own RSVP. The public API never returns organizer notes, source conversations, private budgets, participant lists, ballot votes/tallies or other individual RSVPs.

RSVP names are self-reported, required for the organizer’s attendance view and not shown to other guests. Names confer **no permission**; matching names can be different credentials. The browser generates/stores a separate random RSVP edit credential and submission ID before sending, under a **plan-ID-specific** localStorage key. Voting and Section 6 question credentials use different namespaces and do not create RSVPs. The same guest may vote for one option and RSVP Can’t make it to the chosen plan. Clearing site data/another device loses edit permission; a shared browser profile can reuse it. This is not authenticated one-person-one-RSVP: forwarded links or a new browser can create additional responses.

POST retries reuse the submission ID/edit credential and return the existing own response rather than double-counting or silently changing it. PUT changes use a revision and stable request ID. Duplicate clicks are guarded in the UI and serialized on the server. Immediate owner action/link retries reuse request IDs and their exact payload; an old retry after intervening actions conflicts rather than replaying a mutation. There are no automatic retry loops. Errors preserve local entries and offer deliberate retry/reload.

Every RSVP requires acknowledgment of the current published version. Date, time, zone, meeting point, activity, selected option or cost changes increment a **material version**. Previous Going/Maybe/Can’t responses become **needs reconfirmation** and are excluded from current-choice totals until the respondent submits again. Public instructions/source-link/booking-note changes still publish a notice/version but do not alone invalidate attendance intent. A stale open page cannot confirm the newer details: its version fails server validation. A plan publication racing an RSVP either rejects the obsolete submission or stores it as earlier-version intent needing reconfirmation; it never remains counted as current.

Organizer attendance is a compact list of self-reported name, RSVP, update time and reconfirmation flag, plus current counts and total responses. It is independent of vote totals and is **not proof of actual attendance**. No name-matching or vote-to-RSVP conversion occurs. Cancelled/completed/closed plans reject submissions while keeping approved details readable until link expiry/revocation. All plan/response records cascade when the saved session/group is deleted.

## Implementation and bounds

- `packages/planning/src/plans.ts`: strict public/draft/owner/RSVP contracts, clear-clock validation, material-change fingerprint and lifecycle rules. Existing summary and extraction contracts are unchanged.
- Owned `/api/private/sessions/:sessionId/plans`: GET dashboard, POST `/select`, PUT `/draft`, POST `/publish`, `/control`, `/link`, `/revoke`. Existing server Supabase verification and group/session ownership gates apply to every operation. Ballot choices are looked up only in the same owned session. Client-provided content cannot forge a published option.
- Public `/api/plan`: GET `/page` (shared bearer), POST `/rsvps` (shared bearer + private creation credential), GET/PUT `/rsvp` (private edit bearer + X-Invite-Token). Guests cannot enumerate attendance or address another response by a name/ID. no-store/private, no-referrer, nosniff, origin, JSON and body/rate protections reuse Section 6.
- `PlanStore`: owned session/plan locks, strict revision and preview checks, immutable version records, SHA-256 credential digests and latest-mutation hash. RSVP writes lock the same plan row as updates/revocation and recheck link/state/version after locking. A direct privileged DB admin remains outside application-level access guarantees.
- Migration **202611140001_plans** adds `fuzl_shared_plans`, `fuzl_plan_versions`, `fuzl_plan_links`, `fuzl_plan_rsvps`, with uniqueness, indexes, RLS and direct PUBLIC/anon/authenticated revocation. It does not reset existing data. One plan/session, up to 100 published versions (publication stops at 98 to reserve closure/terminal-notice slots), 200 RSVP credentials and bounded public fields. Public rate controls are process-local, not a distributed anti-abuse guarantee.
