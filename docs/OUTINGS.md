## What is stored and who can see it

- **Outing:** one explicit actual record per completed plan, attached to the saved group at recording time. It stores a frozen copy of the original confirmed ballot/plan details and version alongside separately editable actual activity, date, clear local clock/time zone and meeting point. The server rejects future and ambiguous/nonexistent clocks. An explicit same-listing checkbox is required before applying feedback to that source listing; a changed venue does not inherit a boost. Manual ideas without a specific source can retain group history/takeaways without a matching card boost.
- **Attendance:** organizer-entered names are explicitly confirmed by the organizer; guest attendance is a separate explicit self-report. Neither votes, Going RSVPs nor matching names become actual attendance. Names are not authenticated identities and the two lists are not deduplicated by name. Completion does not verify attendance automatically.
- **Feedback:** optional repeat/value questions retain Yes/No/Unsure/unanswered separately, with an optional 500-character note. Only people explicitly reporting attendance can provide answers, notes or memory permission. A guest can retract attendance, clear answers/note and withdraw memory permission. The organizer and author can read that individual response; other guests cannot. Clearing browser data or switching devices loses the private edit permission. Shared profiles can reuse it, and a new credential can create another response: this is not verified one-person-one-response.
- **Notes and memory:** private organizer notes and proposed takeaways are separate from a manually approved, at most 300-character group takeaway. Saving notes/proposals does not approve memory or alter an existing approval. The organizer explicitly reviews current feedback and permission, preserving disagreement, then approves/edits/removes the takeaway. Individual feedback, private notes and proposals are never put into public plan pages or provider inputs. Approved text is visible only in the organizer’s group/history/recommendation flow, not the account-free page. Approval is a human judgment; Fuzl cannot semantically prove a free-text takeaway accurately summarizes permitted observations.

Guest access reuses the current `/plan#invite=…` link, header-only bearer transport, server expiry/revocation checks and the plan-ID-specific browser edit credential. A person need not have voted or RSVPed to report actually attending. Feedback is available after explicit actual completion even though RSVPs are closed; expiry/revocation still closes all access. A replacement link for the same plan can restore the same browser’s own feedback. The public responses contain only the organizer-confirmed actual outing and the caller’s own feedback, never another person’s answer, memory text, counts, group/member IDs, chats or budgets.

## How memory affects the next search

The backend first verifies the organizer and current saved session, then loads **only its group’s approved observations**. The group association is fixed at recording time: moving a saved session does not silently move history to another group. Deleting the original group or session cascades its dependent outing/feedback; no cross-group copy is made.

For recommendation calculations the server reads only the approved text, original public source reference, actual date, current approval/version and minimal consent/attendance/repeat opinions. It does not load notes/names/value answers for ranking and does not compare aliases to participants. All explanations are dated group-level observations about permitted feedback from self-reported attendees, never claims about specific people or permanent personal preferences. If attendee identities are unclear, no person-specific inference is attempted.

Only an **exact source URL** match to an explicitly confirmed visited listing receives an annotation. No fuzzy name matching, category-wide preference or venue-to-different-event inference occurs. The most recent approved matching outing supplies one bounded preference adjustment: all permitted repeat ratings Yes → +2; all No → no boost with a negative label; disagreement/Unsure → no boost with a mixed label; no permitted current ratings → no boost with an unrated label. Cost-worth responses may inform the human takeaway but do not establish a current price or override affordability. Current firm budget, timing, radius, address and other checks still determine eligibility before preference ranking; cancelled events remain excluded and uncertain events stay uncertain.

Any guest answer, attendance or permission change suspends approved use. Actual-detail corrections increment the actual version, mark prior feedback as needing review and suspend use. Fresh guest responses must acknowledge the current actual version. An organizer cannot accidentally reapprove an unseen feedback revision: writes compare both outing and feedback revisions under row locks. New searches load the current approval; search context fingerprints include memory revisions, so changes during a request or evidence recheck reject stale context. Already rendered cards are snapshots: deliberately refresh/search to update them. No provider request contains memories, private answers, chats or participant information.

## Important code and request flow

- `packages/planning/src/outings.ts`: actual/feedback/owner/public contracts; minimal history DTO; explicit attendance and optional answers. `memory.ts`: bounded group-level sentiment/matching rules. Existing evaluation functions accept server-supplied memories after constraint calculation; cards display a separate memory box, not a provider fit check.
- Owned `/api/private/sessions/:sessionId/outings`: GET record/feedback, POST `/complete`, PUT `/actual` and `/memory`. Group history is GET `/api/private/groups/:id/outings` and returns compact fields only. Supabase server verification and group/session ownership gates cover every owner route.
- Guest `/api/plan/outing`, POST `/feedbacks`, GET/PUT `/feedback`: shared-link permission plus a private response edit credential. The UI persists its credential/submission ID before sending. Creation retries return the existing own response; edit request IDs and revisions protect repeated sends and stale edits. Shared-link tokens cannot act as edit credentials, and names grant no authority. Guest JSON/body/origin/rate/security headers reuse Section 6. No raw-conversation, credential or connection logging was added.
- `OutingStore`: session → plan → outing lock order; completion and the actual record commit together; immutable original plan snapshot; feedback/approval serialize with access revocation and lifecycle mutations. Current feedback and owner writes use revisions/request hashes; UI replacement requires deliberate reload and leaves newer edits intact. No polling or retry loop.
- Migration `202611140002_outings` adds `fuzl_outings` and `fuzl_outing_feedback`, group/plan cascade relations, uniqueness, RLS and direct PUBLIC/anon/authenticated revocation. Bounds: one record/plan, 200 feedback credentials/outing, 100 recent records loaded per group. Rate controls remain process-local. No schema reset, provider catalog, personal profile, new dependency or AI summary was introduced.
