## Provider and development limits

Fuzl uses **Supabase Auth + Supabase PostgreSQL**, with Prisma **7.10.1** migrations/driver adapter and supabase-js **2.119.0**. Supabase combines managed authentication and PostgreSQL in one project, works with the existing React/Vite + Express architecture, and avoids app password storage or custom authentication cryptography. Sign-in uses the **default email magic link**, with provider-managed account creation on first verified sign-in. No template editing, custom SMTP, password or OAuth implementation is required. Prisma 7 is pinned rather than adopting the current Prisma 8 release candidate.

Official documentation/pricing was checked November 6, 2026. Supabase's Free plan currently lists 500 MB database storage, 50,000 monthly active users, two active projects and pausing after a week of inactivity. Limits can change; verify Free in your organization/project dashboard. The default development email sender is restricted to organization members and currently two messages/hour across the project. This is suitable for an organizer's controlled development test, not unrestricted production email delivery. No billing was enabled or assumed unlimited. [Pricing](https://supabase.com/pricing), [email delivery limits](https://supabase.com/docs/guides/auth/auth-smtp).

```dotenv
SUPABASE_PUBLISHABLE_KEY=sb_publishable_REPLACE_LOCALLY

# Optional migration-only endpoint; configured locally for the macOS issue below.
DIRECT_URL="postgresql://postgres:URL_ENCODED_PASSWORD@db.PROJECT_REF.supabase.co:5432/postgres?sslmode=verify-full&sslrootcert=/ABSOLUTE_PATH/supabase-ca.crt"
# The canonical frontend origin for this local magic-link implementation.
APP_ORIGIN=http://127.0.0.1:5173
```

These are placeholders. The real database URL/password stays backend-only. No VITE_ secret or frontend environment file is needed. `GET /api/account-config` exposes only configured=false, or the project URL and designated publishable key. Gemini/OpenAI keys, DB URL/password, tokens and privileged Supabase keys never appear there. Do not put a service-role/secret key into the publishable setting.

Download the project's CA from **Database settings → SSL Configuration → Download certificate**. Keep a stable copy outside the repository (configured locally under `~/.config/fuzl/`); use its **absolute path** in `sslrootcert` so working-directory changes cannot select another file. The downloaded certificate is a public trust anchor, not a client certificate/private key. Do not add it to system-wide trust or disable verification. Validate that it is a currently valid CA and that the runtime driver actually loads it; this alone does not verify a remote server's identity. [Supabase TLS setup](https://supabase.com/docs/guides/database/connecting-to-postgres#ssl).

The API's `pg` driver uses `sslmode=verify-full&sslrootcert=...`. Prisma **7.10.1's native migration engine uses different parameter names**: `accounts/migration-url.ts`, called by `prisma.config.ts`, derives `sslmode=require&sslaccept=strict&sslcert=...` with the same CA, unchanged credentials and the `fuzl` schema. Here `require` prevents plaintext fallback while `strict` retains certificate/hostname validation. These CLI-specific options must not replace the runtime `.env` parameters: `pg` interprets `sslcert` as a client certificate. The translation also avoids Prisma treating unsupported `verify-full` as `prefer`, or using its permissive default certificate mode. Verified against the [installed engine's URL parser](https://github.com/prisma/prisma-engines/blob/d1b3f377ca835d73fd50954a5e22128b9ebdd6b8/quaint/src/connector/postgres/url.rs) and [native TLS builder](https://github.com/prisma/prisma-engines/blob/d1b3f377ca835d73fd50954a5e22128b9ebdd6b8/quaint/src/connector/postgres/native/mod.rs).

Before any connection, replace password placeholders privately with the project database password (not the Supabase account-login password), removing placeholder brackets. Percent-encode **only the password component, once**; preserve copied host/username and TLS parameters. Do not put passwords in shell commands/history or online encoders. `DIRECT_URL`, when set, selects only the migration connection; an invalid selected URL fails without silently falling back. If omitted/empty, the CLI derives its connection from DATABASE_URL.

**Observed macOS pooler certificate issue:** Prisma's first hosted deploy/status attempts returned a generic schema-engine error. A read-only native-engine diagnostic exposed **P1011, "The certificate was not trusted."** Local macOS trust evaluation of the presented pooler chain reported `OtherTrustValidityPeriod` and `ServerAuthEKU`: its leaf lasts 1,825 days and lacks the required server-authentication usage. The API's Node/OpenSSL driver verifies that chain/hostname, while macOS's native TLS policy rejects it. The direct endpoint presented a 730-day leaf with server-authentication usage; both Node and Prisma native connection checks succeeded. Configuring DIRECT_URL resolved the migration failure without bypassing validation, changing system trust or enabling billing. This is an observed endpoint/platform compatibility issue, not evidence that every future pooler has this certificate. [Apple TLS requirements](https://support.apple.com/en-us/103769).

TLS was checked on the actual client sockets, with encryption, authorization and hostname verification enabled. Behind a pooler, `pg_stat_ssl` describes the pooler-to-database backend connection, not Fuzl's client-to-pooler socket; it reported no TLS for that internal hop. Direct PostgreSQL reported TLS. These checks do not establish the provider's internal network guarantees. The hosted migration created only the expected fuzl tables/history; no reset, seed, application test rows or direct ownership bypass was used to claim a real sign-in/save test.

## How the browser callback establishes a session

This is a React/Vite single-page app, not an SSR/cookie application. It uses Supabase's documented **implicit browser flow**, explicitly selected in the client. The default confirmation/magic link visits Supabase to validate its one-use token, then redirects to the fixed local callback with session credentials in a **URL fragment**. Fragments are not sent to Express/Vite. No custom token-hash template, server callback or PKCE code exchange is required for this architecture. [Browser flow](https://supabase.com/docs/guides/auth/sessions/implicit-flow).

At startup, `accounts/magicLink.ts` captures credentials only from the intended callback and immediately replaces the history entry with `/`, before fetching configuration or rendering React. Query credentials, wrong routes/origins, recovery links, missing/duplicate fields and provider errors are rejected with controlled messages. Raw provider errors, URLs, tokens and email content are never logged/rendered. There is no `next`/`returnTo` navigation input. The browser SDK's automatic URL detection is disabled so it cannot accept credentials elsewhere.

`AccountProvider` waits for `auth.setSession` before making the account client available. The SDK verifies the supplied access token with Supabase Auth, or refreshes an expired session, and owns session storage, expiry and cross-tab notifications. Completion runs once per callback, releases its credential references, and cannot replay after sign-out/configuration reload. Only a successful verified email session yields a success notice; link-request success never does. An unavailable API/configuration/network or expired link yields recovery instructions and no fabricated sign-in. [SDK session handling](https://supabase.com/docs/reference/javascript/auth-setsession).

Open the email link **in this browser, preferably a new tab**, leaving the original Fuzl tab open. SDK notifications sign that tab in without reloading; first sign-in and same-account reauthentication preserve its in-memory workspace. In the reauthentication view, choose **Back to saved groups** after completing the link. Changing accounts or ending a session clears previous private memory and cancels pending private work for isolation. Opening the email link in the original tab navigates away and may discard its unsaved memory; the existing navigation guard is best effort. Never rely on a callback to restore unsaved planning data. Backend remote identity verification and ownership/revision checks still run for every private request, irrespective of callback/UI state.

## What is saved, temporary, and reviewed

- PostgreSQL stores an authenticated organizer's provider UUID, owned groups/timestamps/revisions, explicit group aliases, and group-owned sessions. Session records store title, schema version 1, the existing summary JSON, limited text correction provenance, origin, timestamps and revision.
- The save contract permits source-free manually entered facts; the existing AI provider/analysis-response evidence schemas remain strict. Only **fact-cited supporting sources** are included. Unused source text is pruned at the client save boundary and rejected by the server. The complete draft/transcript, raw images, thumbnail URLs and unrelated original messages are not fields in the save contract. Supporting excerpts can still contain private messages/budgets; the save disclosure says so. If many messages support facts, saved excerpts can contain substantial conversation content.
- Screenshot provenance retains only entries linked to saved quotes: screenshot reference, original/reviewed alias and text, visible-time correction and uncertainty. Original screenshots were temporary; reopened evidence shows text provenance with **no image fetches or broken image links**, and never claims pixel/OCR verification.
- Unknown remains null, including budgets; zero stays a known value. Firmness, tentative/conflicting status, historical scope and AI review metadata round-trip. Accepting AI output into the editor does not confirm it; Save does not mark it reviewed. Existing manual fact-application behavior remains.
- Group aliases and session speakers/participants are separate from authenticated organizers. Matching names or emails do not establish ownership/membership. Session-specific budgets/availability do not become group preferences.
- Drafts, unsaved summaries, screenshots and full transcripts remain browser-memory work. Clearing screenshot state does not delete deliberately saved records. Removing a saved record does not erase an already-open working copy; close/clear/sign out to remove that memory. Replacing a summary with a sample/blank/new AI extraction starts a new save context, rather than overwriting an older saved record's provenance.
- **For organizer authentication, the auth SDK session cache** persists in browser localStorage under `fuzl-organizer-auth`; it contains provider session credentials and identity, not planning data. The SDK restores/refreshes it. Section 6 guest pages separately retain invite/response-edit credentials, never typed answer drafts, as documented in GUESTS. Access tokens travel only in Authorization headers; private requests omit cookies. No raw planning data, token, query payload or database URL is logged.

## Authorization, conflicts, and deletion

Every `/api/private` operation independently calls Supabase `auth.getUser(token)` against the configured project. It requires a valid verified, non-anonymous email user. The frontend's cached getSession is only UI state, never server authorization. Owner IDs are absent from accepted request bodies; the backend derives the subject from that verified provider response. [Official server verification guidance](https://supabase.com/docs/reference/javascript/auth-getuser).

Prisma queries always scope the group/session through the organizer's verified subject. Reads, lists, creation, assignments/moves, updates, nested aliases/sources and deletes use that scope. Cross-account IDs return unavailable/404 without exposing records. Fuzl tables have RLS enabled, no browser Data API policies and revoked public grants; the backend DB credential is privileged and never leaves the server. Public configuration and anonymous temporary AI endpoints remain separate.

Private browser requests use the same-origin Vite proxy, exact allowed origins and explicit bearer headers with credentials omitted. There is no ambient cookie authentication and no wildcard CORS. Cross-origin sites cannot supply the token through a credentialed cookie, and mutation JSON requests require authorization. POST/PUT/PATCH bodies are capped at 1 MiB. Bodyless DELETE is supported; origin/token checks still apply.

Session updates atomically require the current revision and increment it. A stale tab gets HTTP 409, retaining its draft/edits. **Open latest version** confirms replacement; **Save as new session** preserves the local alternative. This is optimistic concurrency and JSON schema versioning, not a complete history of every past version. Human value corrections are allowed even when the old quotation no longer supports the new value; saving does not rerun AI or rewrite evidence. Required original source text/speaker references and existing correction provenance cannot be rewritten under the same source IDs (422). Removing a fact can remove now-unused saved excerpts. Group name/alias edits also require a current revision.

Failed writes do not replace editor values or retry automatically. A lost connection can leave a create outcome uncertain; refresh the saved list before retrying a new session. Revisions protect updates, while creates are not a server-idempotent API. Verify sign-in again can reauthenticate the same identity without clearing its workspace; a different identity starts a clean workspace. Signing out immediately clears the private workspace/caches and aborts pending requests, then asks the SDK to revoke the local refresh session and clears its designated cache even on failure. The UI reports when remote revocation could not be confirmed. Account lifetime keys and request cancellation prevent late old-account responses from reappearing. SDK session termination also clears private memory for isolation. Access JWTs can remain valid until provider expiry; local sign-out does not promise immediate global token revocation or deletion of other-device sessions. [Provider session behavior](https://supabase.com/docs/guides/auth/sessions).

Deleting an owned session removes its summary and excerpt/provenance JSON. Deleting a group cascades to its aliases and all sessions. There is no restore UI. A minimal organizer UUID row remains; auth-account deletion is a separate provider/admin action and does not automatically delete app rows. Delete groups first if removing saved application work, then manage the Auth account separately. This release has no account-deletion UI, backup-erasure mechanism, or guarantee about provider backup retention/deletion timing.
