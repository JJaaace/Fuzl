## Normal organizer and guest flow

Reopen an owned saved session. Its **intended roster is every participant in the applied session summary**, displayed by name/unknown name and stable participant ID. Saved group aliases are not authenticated identities and are not matched by name automatically. Add any missing intended group members in the summary, save/reopen that roster, then review participation. A subset never deletes a group alias or session participant; another session defaults to Everyone together.

**Everyone together** checks all intended people, showing confirmed, tentative, unavailable, conflicting or missing availability. Current reviewed facts may establish availability; a missing reply alone never does. An empty roster remains unknown and cannot earn a full-group fit. Historical/unreviewed/tentative facts do not become confirmations.

For **Who’s available?**, expand **Collect opt-ins for one exact window**. Enter a date, start/end and IANA time zone, or choose **Use the selected date (all day)**. Date-only explicitly means available for the full local date and expires at the following local midnight; it is not a guessed outing start. Timed windows currently stay within one local calendar day. Ambiguous/nonexistent local clocks are rejected; the end must be in the next 14 days. Overnight custom windows are not implemented. All-day and timed choices preserve existing firm availability; a person with a conflicting firm partial-day limit cannot be assumed available all day.

Approve the exact window, explicitly allow replacing an active question link if necessary, then **Create window guest link**. Copy the resulting `/guest#invite=…` link privately into your existing chat. Fuzl does not send it. Replacing/revoking this link invalidates old guest-response editing access, as in Section 6. Existing budgets/answers remain separate session records. The ballot and final-plan links use their own credentials and are unaffected.

At that account-free link, a guest first saves a display name and an optional budget (private by default) using the existing response form. **Saving a name or budget does not opt in.** The separate availability panel states the exact date/window and offers Yes / No / Maybe / Unknown. Only explicitly saving **Yes — I explicitly opt in** is affirmative. The same private response-edit credential restores/edits that guest’s opt-in; display-name matches grant no access. The page returns only the approved window and the caller’s own reply, never the roster, other people’s replies or private limits. Retries reuse a request identity; double clicks are blocked. Reloading own availability explicitly replaces the unsent choice.

The organizer chooses **Refresh participation & replies**, explicitly maps each response to a session participant after checking identity through their existing chat, chooses the intended Yes attendees, and approves **Review & use attendance scope**. Only one current-window credential may be mapped to a participant; duplicate aliases do not merge identities. Older session responses can be mapped to associate retained private constraints, but cannot opt anyone into a new window. No/Maybe/missing/expired/revoked responses cannot authorize inclusion. An unknown identity remains unmatched.

Set Places timing or Events dates within the reviewed window, then deliberately search/recheck. Results display mode and attendee count. There is no provider call while typing or changing scope. Refresh/recheck is deliberate; remote edits are detected on refresh and enforced by the server on every evaluation/application/publication. There is no continuous guest polling. Local edits and the local expiry timer hide old cards/previews immediately. A suspended browser may delay that timer; the server clock remains authoritative. After remote replies change, refresh participation, re-review and recheck rather than treating a previously rendered card as current.

## Fit checks, privacy and state

The checking projection temporarily removes only facts clearly attributed to nonselected session participants. All selected personal constraints, whole-group requirements, unknown attribution, unresolved relevant questions, source excerpts and review flags remain in force. The full saved summary is not replaced, pruned or automatically saved. Related questions disappear from that projection only if every explicitly related fact belongs to excluded people. Unattributed questions remain unresolved.

Each selected person’s availability is checked for the actual candidate window. A reviewed opt-in covers only its exact date/zone/window (or a smaller contained window), never another evening. Firm planning availability still applies even after Yes. A No/conflict covering an overlapping window cannot be waived by shifting the start time. Existing availability facts lack individual zones; cross-zone manual comparisons remain unresolved unless the existing resolved-area assumptions support them. Explicit window opt-ins carry a reliable zone; event dates alone or unknown end times do not establish full-duration fit. Existing budgets, access, travel evidence, unknown prices/hours/tickets and event status checks remain unchanged.

Private budgets are filtered **only on the server**: a private answer is omitted only when its response has been explicitly mapped to a clearly excluded person. Selected people’s private answers remain, including unknown values; zero remains known zero. Unmatched private answers remain conservative session constraints. This may block an otherwise promising subset until identity/provenance is clarified; Fuzl does not silently discard an unknown person’s limit or disclose its value/owner. Older retained budgets are not new opt-ins and are not automatically erased by window expiry. No provider receives the roster, response IDs, opt-ins, conversations, private budgets or notes.

Scope/reply/saved-session fingerprints invalidate stale fit results and **Make this work** previews. Scoped evaluations reuse the existing Places/Events fit checks and current approved group memory; preference/memory cannot override a failed firm requirement. Public candidate baselines can be rechecked without a provider request after scope-only changes, while existing private-answer/session/source changes keep their conservative invalidation rules. A new Events date range still requires a deliberate date-bound search.

Make this work uses the same selected-person projection and availability gates. Existing private-feasibility comparison suppression stays intact. Newly recorded shared-origin/access checks are tagged server-side with the reviewed attendee IDs. Travel proof cannot cover newly added people without a fresh shared-origin check; group access proof needs its recorded roster. Legacy untagged checks retain their original explicit whole-group interpretation. A time shift outside an opted-in window is not authorized by those opt-ins; collect a new window/review instead. Travel changes still require an explicitly flexible limit and a matching sourced estimate, while every included person’s firm limits stay active. Applying an adjustment retains the original full summary/evidence and existing explicit-save workflow.

Unsaved scope fields participate in unload/sign-out protection. Scope edits pause checking and hide older results while preserving shortlist fields. Failed/stale requests keep local entries; refresh confirms replacing unsaved scope fields. Token refresh/revision changes cannot silently overwrite local scope drafts. Account/group/session replacement uses existing privacy/component lifetimes to discard prior private state and abort old responses. No raw conversation, credential, key, link or private limit is logged.

## Published plans and RSVPs

Changing a working scope never changes a published ballot/plan, vote, RSVP or actual outing. In **Choose & publish a plan**, use **Use reviewed attendance scope in plan draft** deliberately. A session with configured participation requires this copy before publication. This copies only the public mode/count plus an internal proof of the reviewed roster/window. It does not publish. Preview the exact guest details and approve publication through the existing flow.

The guest page receives only intended mode/count, not participant IDs, reply matches, private budgets or proof fingerprints. Count means intended people, not Going RSVPs or actual attendance. Roster/window/mode changes are material even if the count stays the same; a new publication marks previous RSVPs for reconfirmation. Publication revalidates current scope and, for subsets, the planned start inside the active opt-in window. Stale/expired/unreviewed proof must be copied/reviewed again. A scope lock serializes publication with opt-in edits. There is no automatic final-plan cancellation/completion or RSVP conversion when opt-ins expire.

## Model, routes and migration

New additive migration **`202611140004_participation`** adds two RLS-protected tables with direct public/anon/authenticated privileges revoked:

- `fuzl_session_scopes`: one per session, mode/window/current invite, explicit response-to-participant mappings, selected roster, revision, review fingerprint and idempotent owner request identity.
- `fuzl_scope_opt_ins`: one response per scope/invite/guest-response credential, choice/revision/request identity/time; linked to existing guest replies and cascaded on session/group deletion.

Windows reuse `GuestInvite` and `GuestResponse`; edit secrets remain their existing digests. No additional guest account or browser planning-data persistence is added. The only public plan-format extension is optional mode/count; an internal JSON proof makes roster changes material without another SQL table.

Owner endpoints: `GET /api/private/sessions/:id/participation`, POST `/window`, `/review`, `/revoke`, behind existing Supabase verification and ownership/origin checks. Public `GET/PUT /api/guest/participation` uses existing guest rate/size/origin guards, the response-edit credential in Authorization and the active invite in X-Invite-Token. Owner `/api/private/sessions/:id/plans/scope` explicitly copies a reviewed scope into a plan draft. Strict schemas reject forged target-response IDs or free-text edits to the server-derived public count.

Important code: `packages/planning/src/participation*.ts` (contracts, projection, availability/clock gates and fixture), `apps/api/src/participation/` (ownership, locks, mappings/review and guest access), existing Places/Events/context/adjustment evaluators, `apps/web/src/participation/` and the existing GuestPage/SessionDiscovery/plan preview. Scope bounds: 20 intended people, 200 retained session responses/mappings, one active question link/window, one current credential per matched person, 14-day window-end horizon. No automatic retries or new key/dependency/environment setting.
