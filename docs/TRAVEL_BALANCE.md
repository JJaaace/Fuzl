## The deterministic rule

**Off by default**, scoped to the current open session and shared between Places and Events. Reopen/group/account replacement resets it. Toggling reuses loaded assessments and safe ordering hints, with no API/provider request. Previously selected snapshots remain mounted.

The server reads the current owned group's latest 100 recorded completed outings. Within them it takes up to the **five latest actual dates in the last 90 days** with reviewed travel in the chosen mode, fixed **one-way** basis, explicit attendance and known minutes for **every currently selected attendee**. At least **two common outings** and at least **two current attendees** are required. Different modes, round trips, partial groups, missing minutes, cancelled/unconfirmed plans and other groups are not mixed in. The current reviewed participant-to-member mapping must be complete; deleted/replaced IDs do not match by name. The group's history is bounded and incomplete, not a permanent personal profile.

Sum each intended attendee's recorded minutes over those same common outings. If the greatest and least totals differ by less than ten minutes, keep ordinary order. A current option needs known per-person estimates in the same mode for the exact listing key, effective address, date, full window and IANA zone, reviewed no more than **seven days ago**. A future check date is rejected. No straight-line radius or provider distance is converted into minutes. Missing/stale current reviewed estimates add an unresolved travel check; any known current estimate over an included person's confirmed firm limit adds a firm failure, including strict “under” limits and mapped speakers. These checks apply once reviewed estimates are configured, whether the ranking switch is on or off, and never clear other uncertainty.

A supported alternative must reduce the range of cumulative minutes **after this outing by at least five minutes**, reduce this trip by at least five minutes for **each attendee tied for the highest prior burden**, and increase the group's total current minutes by no more than ten. This avoids manufacturing balance just by making everyone travel farther. There is no individual score in a response or explanation.

Ordinary fit checks, approved memory and Balanced/Familiar favorites/Something new run first. The tie-breaker then makes at most **one adjacent move per option**, only between **verified fits** with identical check-status profiles, equal approved-memory boosts, the same active discovery-preference tier, and the same supported activity-preference/check-count tier (Places) or provider-status tier (Events). Ordinary proximity/date ordering breaks ties when travel has no supported improvement. Needs-checking and excluded options retain their category and order. A mode favoring a different explicit history tier wins over this travel tie-breaker. Private budgets, firm availability, travel and accessibility constraints remain in force. No current candidate can be made eligible by past travel or approved memory.

Only generic candidate-key ordering hints leave the server in organizer results, and only the winning moved card displays **Helps balance travel across recent outings.** No private amounts, origins, names, historical totals, individual durations or burden scores appear there. Insufficient data or an already preferred order keeps normal ranking with an honest explanation.

## State, ownership and storage

- `packages/planning/src/travel-balance.ts` defines strict contracts, evidence matching, added firm/unknown checks and server-only calculations. `apps/web/src/travel/ranking.ts` applies the bounded hints after existing discovery preferences. The fixture has no authority over real data.
- `TravelStore` verifies the owner through the existing Supabase-protected private router, binds current estimates to saved session revision and reviewed scope key, and validates every alias against that group and participant against that session. Histories belong to the outing's original group, even if its source session moves. Public outing/plan/ballot/guest DTOs explicitly omit the new fields. Provider allowlists are unchanged; there is no new provider call or origin lookup.
- Private GET/PUT `/api/private/sessions/:sessionId/travel` supplies/replaces session setup. PUT `/travel/history` updates/deletes the actual completed outing for that session. Session → plan → outing locks, revisions, request hashes and retained request IDs protect concurrent edits, double clicks and deliberate retries. Stale writes return a useful error; entries survive errors. Explicit reload/replacement guards and existing unload/sign-out protections cover unsaved travel forms.
- Scope changes suspend the stored setup until explicit review/save against the new scope. Travel revisions join the full search/helper context fingerprint, so history changes during a request reject it; ordinary source snapshot fingerprints exclude travel-only edits, allowing deliberate same-candidate rechecks. Changes to actual visit evidence or approved feedback still invalidate those source/history snapshots. There is no polling: another tab's edits become visible on deliberate reload/recheck. Already loaded results remain last-check snapshots until refreshed.
- Additive migration **`202611140005_travel_balance`** adds nullable private JSONB `travelReview` columns to existing `fuzl_sessions` and `fuzl_outings`. Session data contains its own revision/request identity; outing changes reuse its existing revision/request protection. Existing table RLS and direct PUBLIC/anon/authenticated privilege revocations apply. No new table, dependency, key, reset, origin database, public fairness score or guest preference collection.
