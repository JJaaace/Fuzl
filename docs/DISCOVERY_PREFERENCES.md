## Ranking behavior

**Balanced** keeps the existing deterministic ordering, including its current small approved-memory preference. **Familiar favorites** gives a small additional position bonus only to an exact recorded visit with current approved positive group repeat feedback. **Something new** favors a reliably identified listing without a recorded visit in this group. A saved idea can qualify; saving it is not an actual visit.

The preference operates independently inside **Fits checked constraints** and **Needs checking**. It never changes fit checks, known exclusions, event cancellation/status, firm budgets/availability/travel/accessibility requirements or unresolved evidence. Excluded options retain their normal ordering. Each qualifying row gets a two-point bonus against its position in the balanced category, ties retain balanced order; a modest bounded move, never a new feasibility score. Every toggle starts from the original balanced list. The existing top-three useful-card limit and three-option shortlist limit remain.

Each category needs comparable evidence before changing: Familiar needs a favorite and another candidate; Something new needs a recorded visit and a candidate with no visit recorded. If the evidence is insufficient, or the preferred order is already the usual order, an explicit notice explains why no change occurred. There is no novelty claim from a group that simply has no history, no “hidden gem”/exclusive quality claim and no inference about a particular person's preferences.

The server now includes the same already-checked, bounded candidate pool (up to 23 places/events) in the private search result, before top-three truncation. The client can therefore reconsider the current page without another provider request or applying a fresh private budget on the client. It sees only the same general private-feasibility checks, never limits/owners. Selected saved-idea overflow cards retain their existing review behavior. No new candidate or provider page is fetched on a mode change. Older results without a full pool/history metadata keep the available normal order conservatively.

## History and privacy

An owned session determines its current saved group on the server. The completed-outing query reads only identity/revision, the explicit same-listing flag and the original public snapshot needed to obtain its source reference. It does not read attendance names, private notes, raw chats or individual feedback. Votes, Going RSVPs, cancelled plans, unconfirmed plans and shortlist candidates are not visits. Current approved memory is still computed by the existing consent/approval rules; only its approved positive sentiment can create a favorite. Mixed/negative/unrated feedback stays distinct and never earns that boost.

Matches use the existing organizer-confirmed **same listing** relationship and exact specific source URL. There is no fuzzy name/address/person matching. Attribution homepages are excluded by the existing typed source-link helper. Missing source links remain **Visit match unknown**. If an actual outing changed venue without an explicit match, unmatched candidates remain unknown rather than being advertised as new. Reading is bounded to the latest 100 completed outings (a 101st detects truncation); truncated/uncertain history likewise withholds novelty claims for unmatched listings. Known exact matches can still be recorded/favorites. An existing exact approved-memory match also proves a completed, explicitly matched outing even if older than the bounded general-history read; it remains usable, consistent with the existing memory label. Otherwise an unmatched reliable listing says **No visit recorded**, never “never visited.” Different URLs are not silently merged into a personal history.

Only minimal per-candidate state, favorite flag and a short explanation leave the server, alongside existing approved group memory. Other groups' source sets and raw history fingerprints are not sent. Group B cannot affect Group A's results. Provider allowlists remain unchanged; no preference, history, note, participant or budget is sent upstream. Public ballot/plan conversions continue to omit discovery metadata, memory and organizer notes.

History is a snapshot from the last successful search/recheck. Mode switches do not refresh it. Existing explicit rechecks use current history; completed-outing revisions join the server context fingerprint so changed history during a request cannot produce an accepted stale response or adjustment preview. Search inputs, applied facts, source evidence, private answers and saved revisions retain their existing stale guards. Mode selection is display state and deliberately does not advance the workspace's planning-edit counter, so a pending valid request can use the latest selection. No automatic retry loop.

The preference lives in the current open session's discovery component, shared by Places/Events. It is not a group preference or permanent personal profile, and is not persisted across reopen/reload. Loaded session/group/account replacement resets Balanced through the existing component/privacy keys. Already shortlisted snapshots, published ballots/plans, votes and RSVPs stay unchanged. Unsaved source checks retain replacement guards; card keys preserve editors when only their order changes.

Important code: `packages/planning/src/discovery.ts` (validated labels and bounded ordering), `place-evaluation.ts` / `event-evaluation.ts` (existing balanced checks/full pool), `apps/api/src/outings/store.ts` and `places/store.ts` (minimal current-group history/fingerprints), `apps/web/src/discovery/` (control/view/demo), and existing Places/Events finders/cards. No new dependency, environment setting, credential or SQL migration.
