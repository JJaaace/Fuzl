# Section 8A — shortlist and voting

Built on pushed checkpoint `94ed028`. This milestone saves a shortlist, publishes an account-free ballot and collects one choice per guest credential. Votes express preferences only. There is no final-plan selection/confirmation, RSVP, attendance collection, booking, purchase or published final-plan page. Those remain for 8B. No live venue/event/AI request, email, billing change, push, deployment or hosted migration was made.

## Exact local demo

Run `npm run dev`, then open **http://127.0.0.1:5173/?design=ballots**. This development-only simulator uses synthetic fixtures and the real organizer/guest React components, with an explicitly simulated in-memory transport. It makes **no account, API, provider or database request**. It is not evidence of hosted authentication or database acceptance. Reload resets the simulated data; demo links do not work as real server links.

1. In **Organizer demo**, choose **Show demo results**, then **Add to shortlist** on the sample walk.
2. Choose **Events**, enter **November 14, 2026** under **Event search from**, choose **Show demo events**, then **Add to shortlist** on a sample event.
3. Choose **Add manual idea** for a third option. Open **Edit public option details**, replace “New manual idea” with an idea name, and optionally fill time/location/cost/source. Blank amounts stay unknown; entering 0 means a listed zero. Review the default unresolved checks. A fourth choice is blocked.
4. Choose **Save shortlist → Preview ballot**. Confirm the exact public title, option times, locations, costs and links; check the approval checkbox, then **Publish ballot**. The displayed simulated link is not a server link.
5. Choose **Guest ballot demo**, select one radio option, then **Submit vote**. The saved confirmation and last saved choice appear. Select another option and choose **Save vote change**.
6. Return to **Organizer demo → Refresh tallies**. The total stays **one response**, with that response moved to the new option. Counts are not attendance or verified people.
7. Edit a material public detail, **Save shortlist → Preview ballot → approve → Publish revised ballot**. Version 2 starts at zero; version 1 remains visibly superseded with its original votes. The simulated guest view opens the new version and needs a new vote. Choose **Close voting v2**, return to the guest view and **Reload ballot / my vote**: further submissions are disabled. **Revoke voting link** blocks guest access after reload.

## Real saved-session flow

With the existing organizer account and migrations configured, reopen an owned saved session. Its **Save this session** area now contains discovery and **Shortlist & voting**. Discovery cards offer **Add to shortlist**; opening Places or Events, recording venue evidence and editing planning facts retain their established behavior. Shortlisting copies public details from the displayed card; it never selects a final plan, changes the summary, accepts AI claims or modifies guest answers.

The shortlist is saved separately from the summary. **Save session does not save unsaved shortlist edits**; use **Save shortlist**. A label distinguishes saved versus unsaved shortlist content. The normal unload/sign-out/workspace-replacement guards preserve unsaved work, including the shortlist's own dirty marker. Refreshing tallies does not replace local option edits. **Reload saved shortlist** explicitly confirms replacement and will not overwrite newer edits made during its request. Save conflicts preserve the draft; reload/review the current saved shortlist before retrying. A late save records the submitted version while leaving later edits unsaved.

Every publication requires a current saved shortlist, a matching preview and explicit public-data approval. The organizer shares the generated link themselves; Fuzl sends no messages. A new publication always has a new version/link and an immutable option snapshot. A material edit remains a draft until deliberately published as a revision. Old links identify the superseded version and cannot submit more votes; old tallies are never mixed with current votes. Even an unchanged republish creates a new ballot rather than moving old votes silently. Saving/reopening the organizer workspace can recover snapshots/tallies, but not a plaintext shared token; publish a revision if its link was lost.

Use **Refresh tallies** for current counts; there is no background polling. Every version shows its state, per-option count and total responses. Ties are explicitly labeled; there is no automatic winner, tie-break, RSVP count or final-plan action. **Close voting** stops writes while allowing ballot/own-vote reads until expiry or revocation. **Revoke** blocks all guest reads/writes for that version. Supersession and closing do not erase historical votes. Session/group deletion cascades through drafts, ballots and votes.

## Public fields and uncertainty

Only a strict, approved title and up to three public option snapshots reach guests: option ID/type/name, time/location, listed cost/currency/basis/certainty, at most three useful public source links, unresolved checks and a sample-data flag. No arbitrary session/summary object, source conversation, private budget, participant list, organizer note, private feasibility result, digest, tally or other guest vote is included. Discovery-to-shortlist helpers construct an explicit allowlist and do not copy assessment/check objects. Manually entered fields are public by design; do not paste private notes into them.

Places retain the effective location/price and useful source/map labels, proposed timing, unresolved address/hours/travel/booking/group requirements and any exclusion warning. Events retain the provider-listed local date/time/zone/status, venue, starting versus total price, specific listing link, missing duration, fees and other open checks. A starting price is never promoted to a known total. A blank amount remains null; zero remains zero. Unknown currencies/bases and manually entered ideas stay explicit. Sample options are labeled sample data. Links reject unsafe protocols, embedded username/password and credential-bearing query/fragment parameters. Public text is rendered as React text, not HTML.

Selected options are snapshots. Changing a discovery source or a planning constraint does not silently rewrite a saved shortlist or published ballot; review/edit the snapshot, then publish a new version. An option previously excluded by discovery carries a warning. Votes cannot waive firm constraints or make cancelled events feasible; all final feasibility/selection work is deferred. No automatic official-venue verification is added.

## Guest permission, retries and boundaries

`/vote#invite=…` is separate from the Section 6 `/guest` question form. The fragment is removed before React/network work. A distinct sessionStorage slot remembers the voting invite in that tab. Account-free entry never initializes organizer sign-in. Shared tokens are sent only in headers over localhost/HTTPS, not API URL parameters. API responses use no-store/private, no-referrer and nosniff protections.

The guest picks exactly one option and submits, sees **Vote saved**, and can change it while open. Before any send, the browser generates and stores a separate random edit credential and submission ID in a ballot-specific localStorage slot, using the existing Section 6 credential helpers. Reload can restore only that credential's last saved vote; the typed choice is not persisted. Display names are not collected for voting and cannot confer any permission. The shared ballot credential is explicitly rejected as an edit credential.

POST retries reuse the same submission ID/edit credential and count once. If a first send arrived but its reply was lost, retry returns the existing vote rather than creating another or silently changing its choice. PUT changes use a revision plus a stable request ID, so an identical edit retry succeeds once; another stale edit conflicts. Double-clicks are blocked locally and serialized/idempotent on the server. Errors retain the selection and offer explicit retry/reload; there are no automatic retry loops. Server checks ballot scope, state, expiry, revocation, option membership and private edit digest on every read/write. Old-version credentials never edit new-version votes.

This is not verified one-person-one-vote: another browser/profile, cleared site data or a forwarded link can create another response. Anyone with access to the same browser profile may use its stored credential. Losing that permission cannot be repaired by a matching name. Counters are credential-scoped responses, not identified people or attendance. Public endpoints share Section 6's strict origin/JSON handling, 16 KiB body bound and per-IP 60-read/12-write per minute limits; there are at most 200 votes per ballot, 30 published versions per session and three options per version. These are single-process development limits, not a distributed abuse-prevention guarantee.

## API and persistence

- Shared strict schemas/snapshot helpers: `packages/planning/src/ballots.ts`. Existing planning-summary and extraction contracts are unchanged.
- Owned endpoints under `/api/private/sessions/:sessionId/ballots`: GET dashboard; PUT `/shortlist`; POST `/publish`; POST `/:ballotId/close` or `/revoke`. The existing remote Supabase identity verification precedes every route. Store queries scope session/ballot IDs through group ownership. Saved-session revision, shortlist revision and expected current ballot ID reject stale publishing.
- Public `/api/ballot`: GET `/form` (shared bearer); POST `/votes` (shared bearer + submission/edit token in body); GET/PUT `/vote` (private edit bearer + X-Invite-Token). These routes return only approved ballot data or the guest's own vote, never tallies or names.
- `BallotStore` stores only SHA-256 token/edit digests, immutable public snapshots, version/control metadata and votes. Client-generated cryptographically random publication credentials allow an idempotent owner publication retry without storing its plaintext token. The shared token is returned only to the owner who supplied it. It is never logged. Section 6 question-form links/answers are separate and continue working.
- Saves/publications serialize on the owned saved-session row. Votes, revision and close/revoke serialize on the ballot row and recheck state after locking. A close racing a submission can include a vote committed before closure; no write after the closed state is accepted. JSON snapshots avoid coupling historical votes to editable discovery results. Source/provider data is minimal planning context retained for the ballot service/version history, not a copied venue/event catalog; existing provider terms and source staleness still apply.

Migration **202611120001_ballots** adds only `fuzl_ballot_shortlists`, `fuzl_ballots`, `fuzl_ballot_votes` and their session relations/indexes. RLS is enabled, direct PUBLIC/anon/authenticated access is revoked, and existing tables/data are not reset. Credentials, private budgets and conversation tables are not copied. Raw vote/ballot credentials remain out of logs/source/frontend environment configuration.
